# IronClaude Development

## Architecture

Single repo, Postgres-backed. There is no longer a separate `fitness-data` repo — the importer (`npm run import`) migrated each user's markdown into the database.

**Data plane:** Supabase — Postgres (`DATABASE_URL` points at the Supabase pooler), Auth (phone OTP via Twilio), and Storage (the `progress-photos` bucket).
**Compute plane:** Fly.io — Docker container running Express + the inbox worker.

- **Channels** (Telegram today, web/WhatsApp later) post to `/api/webhook` and enqueue an inbox row.
- **Inbox worker** (`src/inbox/worker.ts`) pulls items, takes a Postgres advisory lock keyed on `user_id`, and runs the `CoachAgent` for one turn. The lock guarantees per-user serialization across any number of app instances.
- **Storage** is the Drizzle-backed `Storage` interface in `src/storage/db.ts`. All coach tools call it; they never touch the filesystem. Binary blobs (progress photos) live in Supabase Storage; everything else is rows in Postgres.
- **Auth** is Supabase Phone-OTP. Server-side verification lives in `src/auth/`.

### Tiers

Access control has three states: `trial`, `regular`, `athlete`, `expired`.

- New signups start on `trial` (30 days).
- The `GET /api/cron/trial-expiry` job (daily 9am) auto-flips trials past their expiry to `expired`.
- Paid upgrades flow through Stripe — webhook at `POST /api/stripe/webhook` sets `regular` or `athlete`.
- Admin override: `npm run grant-tier -- --phone +1… --tier athlete` writes the tier directly, bypassing Stripe (useful for comps and dev accounts).

Tier checks happen in the request pipeline before reaching the inbox; expired users get a billing prompt instead of a coaching turn.

## Development Guidelines

### Code Style
- TypeScript for all source files
- Prefer async/await over callbacks
- Keep functions small and focused
- **Always run `npm run lint:fix` after making code changes**
- Run `npx knip` periodically to detect unused code/dependencies

### Date Handling
**Always use `src/utils/date.ts` for date manipulations** — never inline `new Date()` formatting.

Key functions:
- `getDateInfoTZAware()` — comprehensive date info (date, time, dayOfWeek, isoWeek, timezone) using `TIMEZONE` env var
- `getTimezone()` — configured timezone (defaults to `America/New_York`)
- `getCurrentWeek(timezone?)` — ISO week string (e.g., `"2026-W05"`)
- `getToday(timezone?)` — `YYYY-MM-DD`
- `getDayNameInTimezone(date, timezone)`
- `formatISOWeek(date)`

### Environment
- Fly.io for deployment (Docker container, Express server, `start.sh` runs `npm run db:migrate` first)
- Supabase Phone Auth for signup
- Postgres for app data (Supabase pooler URL in prod, local Docker in dev)
- Telegram bot for the primary channel; web UI coming
- **Fly CLI**: `~/.fly/bin/fly` (not in PATH by default)

### Testing

Three tiers:

```bash
npm test              # Unit + integration (~10s, no external services)
npm run test:all      # Adds scenario tests
ANTHROPIC_API_KEY=sk-... npm run test:scenarios   # Real model, ~2 min
```

- **Unit tests** — pure functions, parsers, schema. No DB or network.
- **Integration tests** — live against the local Postgres from `docker compose up -d postgres`. They exercise the `Storage` interface and inbox worker.
- **Scenario tests** (`tests/scenarios/`) — spin up an isolated DB schema, seed fixtures via `setupTestScenario()`, run the real `CoachAgent` (Haiku), and assert on DB side effects (rows in `workouts`, `prs`, etc.) plus the assistant's reply.

Existing scenario suites: `workout-logging`, `pr-detection`, `session-flow`, `response-quality`, `plan-flexibility`.

**After changing coaching logic, prompts, or tools, always run scenario tests.**

To add a scenario: extend `tests/scenarios/fixtures.ts`, use `setupTestScenario()` from `setup.ts`, assert via helpers in `assertions.ts`, and instantiate the agent with `createCoachAgent({ userId, model: "claude-haiku-4-5", maxTurns: 15 })`.

### Local Development
- `docker compose up -d postgres` once per machine
- `npm run db:migrate` after pulling new migrations
- `npm run dev` for the watch-mode server
- Test bot commands via Telegram before deploying

## Claude Behavior

### Skills Reference
- `/plan-week` — Weekly planning workflow (includes progressive overload & deload logic)
- `/analyze` — Progress analysis and recommendations

### Telegram Onboarding

On a user's first turn, the agent loads the `onboarding` skill (`src/coach-v2/skills/onboarding.md`) to walk through profile setup — goals, equipment, schedule, limitations. The skill self-uninstalls once `profiles` has the required fields populated.

### Storage Model

All athlete data lives in Postgres. Coach tools call the `Storage` interface (`src/storage/storage.ts`, implemented by `src/storage/db.ts`) — never read or write files for athlete data. The schema is in `src/db/schema.ts`.

Entities:

| Concept     | Table(s)                                    |
|-------------|---------------------------------------------|
| Profile     | `profiles`                                  |
| Learnings   | `learnings`                                 |
| PRs         | `prs`                                       |
| Weekly plan | `weekly_plans`                              |
| Retro       | `weekly_retros`                             |
| Workout     | `workouts`, `workout_exercises`, `workout_sets` |
| Reminders   | `reminders`                                 |
| Messages    | `messages`, `conversation_summaries`        |

### After Logging a Workout
1. Tools persist sets/exercises to the `workouts` family of tables (no file writes).
2. Check for new PRs — the `record_pr` tool writes to `prs` and stores history.
3. Provide brief feedback on the session.
4. Note any patterns by appending to `learnings` via the `add_learning` tool.

### After Creating/Updating a Plan
1. Plan tool writes a row to `weekly_plans` (one per ISO week per user).
2. Summarize changes to the athlete via Telegram.
3. If PRs were mentioned, update `prs`; if patterns emerged, append to `learnings`.

### Nutrition Coaching

Nutrition logging shares the per-day file with the workout — `weeks/YYYY-WXX/YYYY-MM-DD.md` — under a `## Nutrition` section. Each meal is a `### Meal (HH:MM)` block with one item per line and a `_Subtotal: ..._` footer. Frontmatter carries the rolled-up daily totals (`protein_g`, `kcal`, optionally `carbs_g`, `fat_g`) so other code can read totals without re-parsing the meal body.

**Tools** (`src/coach-v2/tools/nutrition.ts`):
- `lookup_food(query, limit?)` — searches USDA FoodData Central, returns top matches with per-100g macros. The agent calls this BEFORE log_meal to ground macros — this is the fix for the fabrication bug where the coach was guessing protein values.
- `log_meal({ meal, items, notes?, date? })` — appends a meal section and recomputes the daily rollup. Auto-creates the daily file if absent. `start_workout` now upgrades a nutrition-only file in place rather than refusing.

**USDA API**: free tier via `USDA_API_KEY` (or `DEMO_KEY` rate-limited fallback). Get a key at https://fdc.nal.usda.gov/api-key-signup.html.

**Macro targets** live in `profile.md` under `## Nutrition` if the athlete has configured them. The current daily rollup is surfaced to the coach in the dynamic state block (`Today's nutrition rollup`) so it can give "you're at X, need Y more by EOD" feedback without an extra tool call.

**Photo input**: meal photos flow through the existing webhook → image block → coach handler path. The prompt instructs the coach to identify visible items, call `lookup_food` for each, then `log_meal`.

### Weekly Planning Flow (Sundays)

Interactive — questions first, then plan:

1. **Cron** (`GET /api/cron/weekly-plan`, Sunday 8pm) — sends coaching questions via Telegram and writes a pending-planning row to the DB (`weekly_plans` with `status='pending'` or a dedicated planning-state row, see `src/storage/db.ts`).
2. **User responds** — webhook handler detects pending planning state and routes input into the plan generator.
3. **Plan generation** — `generatePlanWithContext()` builds the plan from profile + recent workouts + recovery + user input.
4. **State tracking** — all in Postgres; no file-based state.

Key files:
- `src/cron/weekly-plan.ts`
- `src/handlers/webhook.ts`
- `src/storage/db.ts`

### Weekly Analysis
1. **Read** profile, learnings, last 2–4 weeks of plans/workouts via `Storage`.
2. **Analyze** weight progression, volume, RPE, skill progress, fatigue markers.
3. **Update** PRs and learnings.
4. **Create** a retro row in `weekly_retros`.

### Data Updates

All updates go through the `Storage` interface (DB rows, not files):
- Profile, learnings, PRs, plans, retros, workouts — all in Postgres.
- Coach tools mutate these via Drizzle transactions; multi-step ops are atomic per turn.
- For direct DB edits, use `npm run db:studio` (drizzle-kit studio) or `psql $DATABASE_URL`.

No more `git add`/`git push` to a fitness-data repo — the only git activity is to this codebase.

## Device Integrations

### Current Integrations
- **Whoop** — Sleep, recovery scores, HRV, workout strain
  - **OAuth note:** Whoop's token endpoint requires `Content-Type: application/x-www-form-urlencoded` (not JSON) for all token requests. See `src/integrations/whoop/oauth.ts`.

### Using Integration Data

Integration data is normalized and stored per-user in DB (see `integration_metrics` and `integration_tokens` in `src/db/schema.ts`). Tokens are encrypted at rest with `INTEGRATION_TOKEN_KEY` via helpers in `src/crypto/secrets.ts`.

When integrations are configured, recovery data informs training recommendations:
- **80–100% recovery**: Push intensity, good day for PRs
- **60–79%**: Standard training intensity
- **40–59%**: Lighter work or active recovery
- **0–39%**: Prioritize rest

Coach tools read recovery via the `Storage.getRecentIntegrationMetrics()` accessor — no frontmatter parsing required anymore.

### Adding a New Device Integration

1. **Create the folder**: `src/integrations/{device}/`

2. **Implement the files**:
   ```
   src/integrations/{device}/
   ├── index.ts          # Exports
   ├── client.ts         # API client
   ├── oauth.ts          # OAuth flow helpers
   ├── webhooks.ts       # Webhook parsing & normalization
   ├── integration.ts    # DeviceIntegration implementation
   └── setup.ts          # Interactive CLI setup wizard
   ```

3. **Implement `DeviceIntegration`** (`src/integrations/types.ts`):
   - `isConfigured(userId)` — checks `integration_tokens` for this user
   - `getAuthUrl(userId)` / `handleOAuthCallback(userId, code)`
   - `refreshToken(userId)` — reads/writes the encrypted token row
   - `fetchSleep(userId, range)`, `fetchRecovery(...)`, `fetchWorkouts(...)`
   - `verifyWebhook(req)`, `parseWebhook(payload)`

4. **Token storage**: use `src/crypto/secrets.ts` (`encryptToken` / `decryptToken`) when writing to `integration_tokens`. Never store plaintext.

5. **Register** in `src/server.ts`:
   ```typescript
   import { get{Device}Integration } from "./integrations/{device}/integration.js";
   registerIntegration(get{Device}Integration());
   ```

6. **Add metadata** to `src/integrations/registry.ts`:
   ```typescript
   {
     name: "Device Name",
     slug: "device",
     description: "What data it provides",
     available: true,
     scopes: ["required", "oauth", "scopes"],
     docsUrl: "https://developer.example.com",
   }
   ```

7. **Update scripts**: extend `scripts/setup-integration.ts` and add an `npm run setup:{device}` alias.

8. **Tests**: add `src/integrations/{device}/webhooks.test.ts` and integration coverage for the storage round-trip.

### Key Integration Files
- `src/integrations/types.ts` — shared interfaces (`SleepData`, `RecoveryData`, etc.)
- `src/integrations/registry.ts` — registration & discovery
- `src/integrations/storage.ts` — DB-backed metric persistence
- `src/integrations/webhook-handler.ts` — unified webhook router
- `src/crypto/secrets.ts` — token encryption helpers
